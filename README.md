# SEO Content Studio

> 轻量级 SEO 内容战略与执行工作台：从关键词研究、主题集群到文章规划与维护进度。

**当前版本：v0.2.0 · 可编辑演示版**  
**项目阶段：工作流验证 / 数据模型打磨，尚非生产级系统**  
**当前展示品牌：WINDEK**（演示数据沿用 COOWIN 站点历史来源）  
**技术栈：HTML + CSS + Vanilla JavaScript；无需框架、后端或数据库**

---

> **品牌与历史数据说明：** 页面展示品牌已调整为 WINDEK。`data/demo-data.js` 中的 `window.COOWIN_DATA`、原始 `mysite.com` 链接、历史文章记录均予以保留。`assets/app.js` 内的 `coowin-seo-workbench` 备份格式、LocalStorage 键及历史兼容逻辑也不修改，以免破坏已有数据的读取与导入。当前示例 URL 不代表 WINDEK 站点页面，正式使用前须另行导入 WINDEK 的真实数据。

## 一、项目定位

SEO Content Studio 不尝试替代 SEMrush、WordPress 或 AI 写作工具，也不把 SEO 决策自动化。

它解决的问题是：**把分散的关键词研究和内容审计成果，整理成可以审核、执行、追踪并维护的文章计划。**

典型问题包括：

- 哪些关键词值得研究？应该归属于哪个主题与目标页面？
- 哪些主题需要支柱页，哪些适合分支文章？
- 已有文章需要更新、保留，还是另建新文章？
- 规划建议中哪些经过人工核验，哪些只是原始数据中的候选匹配？
- 当前计划的优先级、执行状态和修改意见是什么？
- 如何保存人工判断，同时保留研究快照以供追溯？

### 与 SEO Article Studio 的分工

| 工具 | 职责 | 主要数据 |
| --- | --- | --- |
| **SEO Content Studio（本项目）** | 面向未来的内容战略、规划与执行 | 关键词研究、集群、文章计划、优先级、进度 |
| [SEO Article Studio](https://github.com/coowinit/seo-article-studio) | 面向已发布 WordPress 文章的内容理解和维护 | Site Knowledge、文章关系、重叠检查、内链候选、AI Context |
| SEMrush 等研究工具 | 搜索市场证据 | 搜索量、KD、搜索意图、SERP、排名等 |
| ChatGPT | 结合外部数据与本站知识，协助人工分析、审稿与规划 | 人工提供和审查的上下文 |

**架构原则：两项目独立、职责互补，先通过稳定数据契约关联，不复制对方的核心引擎。** 当前版本没有与 WordPress 或 SEO Article Studio 实际同步。

```text
SEMrush / CSV / 人工研究
          ↓
关键词候选与研究快照
          ↓
SEO Content Studio
  ├─ 内容集群
  ├─ 文章规划
  ├─ 关键词归属
  └─ 执行与审核状态
          ↕  未来：受控的数据交换
SEO Article Studio / WordPress
  ├─ 真实文章及 Post ID
  ├─ Site Knowledge
  ├─ 相关内容与重叠线索
  └─ 内链与更新机会
          ↓
人工核验 → ChatGPT 辅助分析 → WordPress 内容操作
```

## 二、当前功能（v0.2.0）

| 模块 | 已实现 | 说明 |
| --- | --- | --- |
| 内容总览 | ✅ | 集群数量、文章规划数量、工作类型分布、执行完成率 |
| 内容集群 | ✅ | 查看集群及所属文章；编辑名称、支柱主题、备注；集群 ID 不变 |
| 文章管理 | ✅ | 搜索、集群/工作类型/执行状态筛选、分页、详情与规划编辑 |
| 关键词库 | ✅ | 检索样本关键词，查看搜索量、KD、搜索意图，调整人工归属 |
| 本地编辑 | ✅ | 原始数据只读；修改作为覆盖层保存于 `localStorage` |
| JSON 备份 | ✅ | 导入、导出**修改覆盖层**；支持确认后重置本地修改 |
| WordPress 同步 | ❌ | 尚未实现；不能自动修改、发布或校验站内文章 |
| 完整研究库 | ❌ | 当前只有 400 条关键词样本，并非完整关键词数据库 |
| 多人协作 / 云保存 | ❌ | 尚未实现 |

### 当前演示数据

- **10 个内容集群**。
- **160 条文章规划**（原规划包含 20 条新建、86 条优化、54 条保留建议）。
- **400 条关键词样本**；原始研究表的完整关键词数据未全部纳入。

这些是从历史内容规划材料整理出的**测试数据**，不是实时 SEO 结论。原始搜索量、KD、URL、旧文章相似度及页面对应关系均可能过时或有误；未经人工检查，不能据此自动创建、改写或合并文章。

尤其要注意：**“内容重叠”不等同于 Google 关键词蚕食；“原始建议优化”不等同于已审核的执行任务。**

## 三、快速开始

1. 下载或克隆本仓库。
2. 在 Windows Chrome 中双击 `index.html`，即可打开本地演示版。
3. 进入「文章管理」，点击「查看 / 编辑」查看和更新文章规划。
4. 进入「内容集群」，点击「编辑集群」更新集群信息。
5. 进入「关键词库」，点击「调整归属」修改人工目标文章、集群、角色及备注。
6. 每次完成一段较重要的工作后，点击右上角「导出完整备份 JSON」，将文件保存到独立备份位置。

**提示：页面可以离线使用，但不会自动把修改写回仓库文件、GitHub 或 WordPress。**

### 数据存储和恢复的真实含义

```text
只读基线：data/demo-data.js
           +
修改覆盖层：浏览器 localStorage
           ↓
当前界面显示的数据
```

- 自动保存依赖**当前浏览器与页面来源**（origin）。移动 HTML 文件、换设备、换浏览器或清理站点数据，都可能使已保存的修改不可见或丢失。
- JSON 导出格式标识为 `coowin-seo-workbench`，当前版本为 `2`。导出的主体是 `edits` 修改覆盖层，**并不包含完整 160 篇文章、10 个集群及 400 条关键词的独立基线副本**。
- 恢复时必须使用兼容版本的 `data/demo-data.js`；建议备份文件和对应版本的仓库源码一起保存。
- 导入将覆盖当前浏览器的修改；重置会清除全部本地修改。执行前先备份。
- 当前导入对格式、字段和值作基本检查，但不等同于完整的数据迁移与版本兼容系统。

## 四、数据设计原则

### 1. 三层数据边界

| 层级 | 示例 | 编辑策略 |
| --- | --- | --- |
| **原始研究证据** | 原始关键词、搜索量、KD、搜索意图、来源日期 | 保留快照；通过重新导入更新，不直接覆盖 |
| **人工规划与判断** | 集群、主关键词规划、目标文章、URL、写作范围、内链、优先级 | 允许修改，并标记审核情况 |
| **工作执行信息** | 工作类型、执行状态、备注、复核意见 | 高频编辑，独立于研究结论 |

### 2. 必须区分的三个状态

- **原始建议 / 工作类型**：新建、优化、保留、待确认。它描述要做什么。
- **审核状态**：待复核、已核实、需重新研究。它描述判断是否可靠。
- **执行状态**：未开始、进行中、待审核、已完成。它描述工作进度。

此外，**业务优先级 P1–P5** 不等于 SEO Article Studio 基于本站关系计算的「更新机会高/中/低」，未来联动时不能互相覆盖。

### 3. 稳定标识和关联

- 当前文章 ID（例如 `A001`）和集群 ID（例如 `C01`）作为固定记录标识使用。
- **已知限制**：当前关键词修改以数组下标为键；替换、插入、重排样本后，旧覆盖数据可能关联到错误关键词。正式导入完整数据之前，必须为关键词建立稳定 `keyword_id` 并制定迁移方案。
- 未来一个规划文章可以具有 `site_id`、`wp_post_id` 和 `target_url`，但**不能仅靠标题或 URL 自动断定是同一篇站内文章**。`wp_post_id` 应在站点范围内解释。
- 外部搜索数据与人工建议要记录来源、抓取时间和复核状态，避免历史数据被误认为实时结论。

### 4. 当前不做的事

本项目不会在未经确认的情况下自动改写文章、插入内链、合并或删除页面；也不打算复制 SEO Article Studio 的 DeepSeek 知识分析、站内内容关系或 AI Context 引擎。

## 五、技术结构

```text
seo-content-studio/
├── index.html           # 四个工作视图与编辑弹窗
├── assets/
│   ├── style.css        # 页面布局、表格与表单样式
│   └── app.js           # 筛选、展示、覆盖层编辑、导入导出
├── data/
│   └── demo-data.js     # 演示研究数据（只读基线）
└── README.md            # 项目定位、边界、开发路线
```

当前采用原生 JavaScript，而非 React/Vue，也没有 Node.js 构建流程。对于目前的单机静态工作台，这样更容易理解、部署和维护。

文件数量少并不意味着可以忽略数据契约：后续必须把**稳定 ID、数据验证、迁移、备份和测试**放在新增功能之前。

## 六、后续开发路线（按优先级，而非盲目堆功能）

### P0 · 建立可靠的数据基石（正式版前必须）

- [ ] 设计带版本的统一数据结构：`clusters`、`articles`、`keywords`、`edits`、`source_metadata`。
- [ ] 为关键词生成稳定 `keyword_id`，替代数组下标；编写 v0.2.0 覆盖层迁移与冲突报告。
- [ ] 增加**真正可独立恢复的完整快照导出**；与当前“仅修改覆盖层”备份明确区分。
- [ ] 加入严格的导入校验、版本识别、引用完整性检查、备份预览及失败回滚。
- [ ] 固定文章、集群与关键词的关系规范；禁止静默覆盖人工调整结果。
- [ ] 校验历史规划中的跨主题错配、错误 URL 和不可靠的「相似文章」候选。
- [ ] 建立基础自动测试及 Windows Chrome 回归检查清单（编辑、筛选、刷新、导入、导出、恢复）。

**完成标准**：同一份完整备份能够在新的干净环境中恢复文章规划与人工编辑；替换或升级数据时不会悄悄错配关键词。

### P1 · 完善内容规划与审核体验

- [ ] 区分原始建议、已确认方案和执行记录；直观显示人工修改标识。
- [ ] 增加目标文章映射复核流程：待检查 / 已匹配 / 不匹配 / 无现有文章。
- [ ] 文章详情中更清楚地展示主关键词、支持关键词和集群内的上下游关系。
- [ ] 优化集群到文章、文章到关键词的双向导航。
- [ ] 必要时加入轻量执行字段（负责人、复核日期、完成日期），避免无意义扩张。
- [ ] 添加可审查的 CSV/JSON 导入流程，先预览再确认入库。

**完成标准**：用户能够按「研究 → 复核 → 规划 → 执行 → 验收」完成一个真实文章任务，而不必回到原来的超大表格。

### P2 · 大规模关键词库与性能

- [ ] 在验证数据结构后，按需导入完整关键词研究数据。
- [ ] 数据按需加载、分页与组合筛选；只有真实性能瓶颈才引入虚拟滚动。
- [ ] 增加去重、异常关键词识别和来源时间标记，但不自动删除研究证据。
- [ ] 建立研究快照更新和差异对比机制，避免新导入数据覆盖历史结论。

**完成标准**：完整关键词数据可查询、可追溯，且不会显著影响工作台初次打开速度。

### P3 · 与 WordPress / SEO Article Studio 的轻量协作

- [ ] 定义 `site_id + wp_post_id` 关联契约，支持人工确认现有文章匹配。
- [ ] 先通过手工导入/导出验证数据交换：文章标题、链接、发布状态、最后修改时间。
- [ ] 需要时由 SEO Article Studio **只读**输出 Knowledge 摘要、文章重叠与缺失内链候选。
- [ ] 同时展示「规划优先级」与「站内维护机会」，不得混为一个分数。
- [ ] 保留人工确认；不做自动改写、自动发布与未经审核的批量操作。

**安全边界**：如果以后通过 WordPress REST API 连接，身份验证和授权必须在服务器端校验；纯静态页面不得嵌入长期有效的管理员密钥。是否将前端托管在 WP 后台，应在真实集成需求明确之后决定。

### P4 · 只有实际需求成立时再评估

- 多站点、多用户、在线保存与权限控制。
- SQLite / WordPress 数据表 / 后端 API。
- 操作历史与协作审核流程。
- 更深入的数据图表或 AI 辅助建议。

这些不是当前承诺的必做功能。**只有实际使用证明收益明显超过维护成本，才纳入开发。**

## 七、首个正式版本的验收门槛

发布 v1.0.0 前至少确认：

1. **数据可信**：原始研究证据、人工规划和工作进度分层清晰；关键映射可追溯。
2. **可恢复**：支持真正独立的完整快照备份、跨环境恢复与升级迁移。
3. **可维护**：字段含义、主键、状态、版本格式和错误处理有明确约定。
4. **可用**：Windows Chrome 中完成完整的增量编辑与导入导出回归测试。
5. **不越界**：不未经审核修改 WordPress、不捏造 SEO 证据、不复制其他工具已有功能。

## 八、开发与发布约定

- **当前 v0.2.0**：功能原型，适合本地测试和收集真实使用反馈。
- 后续版本优先做小范围、可回退、可测试的增量改造。
- 每次涉及数据结构变化，必须说明兼容性、迁移规则和备份要求。
- GitHub 是源码与版本管理平台，**不是当前浏览器编辑数据的自动同步目的地**。
- 发布前核对 README、演示数据、代码行为与 Release 内容一致；不把规划中的功能写成已经完成。

## 九、长期维护原则

> **Evidence First · Human Review · Clear Boundaries · Simple Architecture · Maintainable Data**

1. **先验证事实，再执行 SEO 决策**：搜索量、KD、原始 URL、匹配建议都需要区分数据来源与复核状态。
2. **先稳定数据结构，再增加界面功能**：尤其是稳定 ID、来源记录、备份与迁移。
3. **优先维护已有能力，不为了功能数量引入复杂框架**。
4. **站内历史知识由 SEO Article Studio 负责；内容战略和执行计划由 SEO Content Studio 负责**。
5. **每次迭代解决一个真实问题**，确认测试通过，再 Commit / Release。
